Ниже — готовое ТЗ, которое можно отдавать Cursor как задачу на реализацию.# ТЗ: автоматическая проверка контрагентов в карточке компании

## Цель

Добавить в карточку компании системный нередактируемый блок проверки контрагента.

Блок должен автоматически получать финансовые и юридические данные по компании из внешнего источника по ИНН и/или ОГРН.

Пользователь платформы не должен иметь возможности вручную изменять эти данные.

Источник данных на первом этапе может быть любой подходящий: Контур, Check.ru, ФНС или другой API. Архитектуру необходимо сделать так, чтобы источник можно было в дальнейшем заменить без переделки всей системы.

---

## 1. Какие данные необходимо получать

### Финансовые данные

Получать данные минимум за два последних доступных отчётных года:

* выручка компании;
* чистая прибыль;
* год отчётности.

Дополнительно автоматически рассчитывать:

* изменение выручки в рублях;
* изменение выручки в процентах;
* изменение прибыли в рублях;
* изменение прибыли в процентах.

Пример:

**Выручка**

* 2024 — 128 400 000 ₽
* 2025 — 151 700 000 ₽
* динамика: +18,1%

**Чистая прибыль**

* 2024 — 8 200 000 ₽
* 2025 — 5 100 000 ₽
* динамика: −37,8%

---

## 2. Исполнительные производства

Получать информацию об исполнительных производствах компании.

Минимально необходимо хранить:

* количество исполнительных производств;
* количество активных исполнительных производств;
* общую сумму исполнительных производств, если источник её предоставляет;
* дату получения данных.

Если API позволяет получать отдельные производства, желательно также сохранять:

* номер исполнительного производства;
* дату возбуждения;
* сумму;
* статус;
* предмет взыскания.

---

## 3. Арбитражные дела

Получать информацию об арбитражных делах, где проверяемая компания выступает именно **ответчиком**.

Минимально отображать:

* общее количество дел в качестве ответчика;
* количество дел за последние 12 месяцев;
* количество дел за последние 24 месяца;
* общую сумму требований, если данные доступны.

Если источник позволяет, дополнительно хранить список дел:

* номер дела;
* дата;
* истец;
* сумма требований;
* статус дела;
* ссылка на карточку дела во внешнем источнике.

Важно: дела, где компания является истцом, не должны попадать в показатель «арбитражные дела в качестве ответчика».

---

## 4. Идентификация компании

Основной ключ поиска во внешнем сервисе:

`ИНН`

Дополнительный ключ:

`ОГРН`

Если ИНН отсутствует, автоматическую проверку не выполнять.

В карточке компании необходимо предусмотреть системные поля:

```text
inn
ogrn
```

Если они уже есть в базе — использовать существующие.

## 5. Новая структура данных

Не смешивать полученные данные с основной таблицей компаний.

Создать отдельную сущность, например:

```text
company_checks
```

Пример полей:

```text
id
company_id

source
source_company_id

revenue_year_1
revenue_value_1

revenue_year_2
revenue_value_2

revenue_change
revenue_change_percent

profit_year_1
profit_value_1

profit_year_2
profit_value_2

profit_change
profit_change_percent

enforcement_total_count
enforcement_active_count
enforcement_total_amount

arbitration_defendant_total_count
arbitration_defendant_12m_count
arbitration_defendant_24m_count
arbitration_defendant_total_amount

risk_score

checked_at
source_updated_at

created_at

```

`raw_data` хранить в JSON/JSONB.

Он нужен для сохранения полного оригинального ответа внешнего API.

Это позволит в дальнейшем доставать дополнительные показатели без повторного запроса внешнего сервиса.

---

## 6. История данных

Необходимо предусмотреть сохранение истории проверок.

Не перезаписывать финансовую и юридическую информацию безвозвратно.

Желательная модель:

```text
company_check_snapshots
```

Каждое обновление создаёт snapshot состояния компании.

Это позволит впоследствии показывать:

* рост количества судов;
* рост исполнительных производств;
* изменение финансового состояния;
* историю изменения риска контрагента.

---

## 7. Слой интеграции

Не привязывать бизнес-логику непосредственно к конкретному API.

Создать единый интерфейс провайдера, например:

```python
class CompanyCheckProvider:
    def get_company_data(self, inn: str, ogrn: str | None = None):
        ...
```

Реализации:

```text
KonturProvider
CheckRuProvider
FNSProvider
```

Внутри приложения должен использоваться единый сервис:

```text
CompanyCheckService
```

Пример:

```python
CompanyCheckService.check_company(company_id)
```

Таким образом, если в дальнейшем меняется внешний сервис, остальное приложение менять не потребуется.

## 9. Ручное обновление

Добавить возможность запросить новое обновление данных.

Например:

```http
POST /api/companies/{company_id}/check/refresh
```

Кнопка в интерфейсе:

**Обновить данные**

Но пользователь не редактирует показатели — он только запускает повторную проверку.

После нажатия:

```text
Обновление данных...
```

После успешного запроса:

```text
Данные обновлены 24.08.2026 в 12:40
```

## 10. Автоматическое обновление

Рекомендуемая периодичность:

**1 раз в сутки**

Не делать запрос во внешний API каждый раз при открытии карточки компании.

Логика:

```text
пользователь открыл компанию
        ↓
проверяем checked_at
        ↓
данным меньше 24 часов?
        ↓
ДА → показать сохранённые данные
НЕТ → поставить задачу обновления
```

Если API дорогой или есть лимиты запросов, период обновления вынести в настройку:

```env
COMPANY_CHECK_TTL_HOURS=24
```

## 12. Цветовая индикация

Финансовую динамику отображать визуально.

Например:

```text
↑ +15%       зелёный
→ 0%         нейтральный
↓ −20%       красный
```

Для юридических рисков использовать предупреждения.

Например:

```text
0 исполнительных производств        🟢
1–3                                 🟡
4+                                  🔴
```

Это только первоначальная визуализация.

Пороговые значения вынести отдельно, чтобы их можно было изменить.

## 13. Рейтинг риска

Подготовить систему для внутреннего скоринга контрагента.

Не смешивать рейтинг с исходными данными.

Исходные данные должны храниться отдельно.

Например:

```text
risk_score = 0..100
```

и:

```text
LOW
MEDIUM
HIGH
CRITICAL
```

В интерфейсе:

```text
Риск контрагента

СРЕДНИЙ

58 / 100
```

Первоначальную формулу можно сделать простой.

Например:

```text
падение выручки > 30%             +20 риска
убыток                             +20
активные исполнительные > 3       +20
арбитражных дел > 5               +20
крупная сумма требований           +20
```

Но архитектурно формулу необходимо вынести в отдельный сервис:

```text
CompanyRiskService
```

Например:

```python
CompanyRiskService.calculate(check_data)
```

## 14. Важное требование по UI

Все данные этого блока являются:

```text
SYSTEM / READ ONLY
```

Обычный пользователь не должен видеть поля ввода.

То есть нельзя делать:

```text
Выручка: [___________]
```

Нужно отображать:

```text
Выручка: 151 700 000 ₽
```

Дополнительно показать подпись:

```text
Данные получены автоматически из внешнего источника
```

и:

```text
Последняя проверка: 24.08.2026 12:40
```

## 15. Ошибки внешнего API

Ошибки внешнего сервиса не должны ломать карточку компании.

Если сервис недоступен:

```text
Не удалось обновить данные.

Показаны данные последней успешной проверки от
23.08.2026 14:20.
```

Если компания не найдена:

```text
По указанному ИНН данные не найдены.
```

Если ИНН отсутствует:

```text
Для автоматической проверки необходимо указать ИНН компании.
```

* получение данных по ИНН;
* выручка за последние два доступных года;
* прибыль за последние два доступных года;
* динамика выручки;
* динамика прибыли;
* количество исполнительных производств;

* сумма требований, если доступна;

Не усложнять первую версию.

## 21. Критерии готовности

Функция считается реализованной, если:

1. В карточке компании с ИНН появляется блок «Проверка контрагента».
2. Все данные приходят автоматически с backend.
3. Пользователь не может их редактировать.
4. Видна выручка минимум за два года.
5. Видна прибыль минимум за два года.
6. Рассчитывается динамика финансовых показателей.
7. Видно количество исполнительных производств.
8. Видно количество арбитражных дел, где компания является ответчиком.
9. Видна дата последнего обновления.
10. Видно название источника.
11. При недоступности внешнего API карточка компании продолжает работать.
12. Результат проверки кешируется.
13. Есть возможность вручную обновить данные.
14. API-ключ внешнего сервиса находится только на backend.
15. Исходный ответ внешнего API сохраняется в `raw_data`.

## Главный принцип реализации

Нужно реализовать:

# ТЗ: автоматическая проверка контрагентов в карточке компании

## Цель

Добавить в карточку компании системный нередактируемый блок проверки контрагента.

Блок должен автоматически получать финансовые и юридические данные по компании из внешнего источника по ИНН и/или ОГРН.

Пользователь платформы не должен иметь возможности вручную изменять эти данные.

Источник данных на первом этапе может быть любой подходящий: Контур, Check.ru, ФНС или другой API. Архитектуру необходимо сделать так, чтобы источник можно было в дальнейшем заменить без переделки всей системы.

---

## 1. Какие данные необходимо получать

### Финансовые данные

Получать данные минимум за два последних доступных отчётных года:

* выручка компании;
* чистая прибыль;
* год отчётности.

Дополнительно автоматически рассчитывать:

* изменение выручки в рублях;
* изменение выручки в процентах;
* изменение прибыли в рублях;
* изменение прибыли в процентах.

Пример:

**Выручка**

* 2024 — 128 400 000 ₽
* 2025 — 151 700 000 ₽
* динамика: +18,1%

**Чистая прибыль**

* 2024 — 8 200 000 ₽
* 2025 — 5 100 000 ₽
* динамика: −37,8%

---

## 2. Исполнительные производства

Получать информацию об исполнительных производствах компании.

Минимально необходимо хранить:

* количество исполнительных производств;
* количество активных исполнительных производств;
* общую сумму исполнительных производств, если источник её предоставляет;
* дату получения данных.

Если API позволяет получать отдельные производства, желательно также сохранять:

* номер исполнительного производства;
* дату возбуждения;
* сумму;
* статус;
* предмет взыскания.

---

## 3. Арбитражные дела

Получать информацию об арбитражных делах, где проверяемая компания выступает именно **ответчиком**.

Минимально отображать:

* общее количество дел в качестве ответчика;
* количество дел за последние 12 месяцев;
* количество дел за последние 24 месяца;
* общую сумму требований, если данные доступны.

Если источник позволяет, дополнительно хранить список дел:

* номер дела;
* дата;
* истец;
* сумма требований;
* статус дела;
* ссылка на карточку дела во внешнем источнике.

Важно: дела, где компания является истцом, не должны попадать в показатель «арбитражные дела в качестве ответчика».

---

## 4. Идентификация компании

Основной ключ поиска во внешнем сервисе:

`ИНН`

Дополнительный ключ:

`ОГРН`

Если ИНН отсутствует, автоматическую проверку не выполнять.

В карточке компании необходимо предусмотреть системные поля:

```text
inn
ogrn
```

Если они уже есть в базе — использовать существующие.

---

## 5. Новая структура данных

Не смешивать полученные данные с основной таблицей компаний.

Создать отдельную сущность, например:

```text
company_checks
```

Пример полей:

```text
id
company_id

source
source_company_id

revenue_year_1
revenue_value_1

revenue_year_2
revenue_value_2

revenue_change
revenue_change_percent

profit_year_1
profit_value_1

profit_year_2
profit_value_2

profit_change
profit_change_percent

enforcement_total_count
enforcement_active_count
enforcement_total_amount

arbitration_defendant_total_count
arbitration_defendant_12m_count
arbitration_defendant_24m_count
arbitration_defendant_total_amount

risk_score
risk_level

checked_at
source_updated_at

raw_data
created_at
updated_at
```

`raw_data` хранить в JSON/JSONB.

Он нужен для сохранения полного оригинального ответа внешнего API.

Это позволит в дальнейшем доставать дополнительные показатели без повторного запроса внешнего сервиса.

---

## 6. История данных

Необходимо предусмотреть сохранение истории проверок.

Не перезаписывать финансовую и юридическую информацию безвозвратно.

Желательная модель:

```text
company_check_snapshots
```

Каждое обновление создаёт snapshot состояния компании.

Это позволит впоследствии показывать:

* рост количества судов;
* рост исполнительных производств;
* изменение финансового состояния;
* историю изменения риска контрагента.

---

## 7. Слой интеграции

Не привязывать бизнес-логику непосредственно к конкретному API.

Создать единый интерфейс провайдера, например:

```python
class CompanyCheckProvider:
    def get_company_data(self, inn: str, ogrn: str | None = None):
        ...
```

Реализации:

```text
KonturProvider
CheckRuProvider
FNSProvider
```

Внутри приложения должен использоваться единый сервис:

```text
CompanyCheckService
```

Пример:

```python
CompanyCheckService.check_company(company_id)
```

Таким образом, если в дальнейшем меняется внешний сервис, остальное приложение менять не потребуется.

## 9. Ручное обновление

Добавить возможность запросить новое обновление данных.

Например:

```http
POST /api/companies/{company_id}/check/refresh
```

Кнопка в интерфейсе:

**Обновить данные**

Но пользователь не редактирует показатели — он только запускает повторную проверку.

После нажатия:

```text
Обновление данных...
```

После успешного запроса:

```text
Данные обновлены 24.08.2026 в 12:40
```

---

## 10. Автоматическое обновление

Рекомендуемая периодичность:

**1 раз в сутки**

Не делать запрос во внешний API каждый раз при открытии карточки компании.

Логика:

```text
пользователь открыл компанию
        ↓
проверяем checked_at
        ↓
данным меньше 24 часов?
        ↓
ДА → показать сохранённые данные
НЕТ → поставить задачу обновления
```

Если API дорогой или есть лимиты запросов, период обновления вынести в настройку:

```env
COMPANY_CHECK_TTL_HOURS=24
```

## 12. Цветовая индикация

Финансовую динамику отображать визуально.

Например:

```text
↑ +15%       зелёный
→ 0%         нейтральный
↓ −20%       красный
```

Для юридических рисков использовать предупреждения.

Например:

```text
0 исполнительных производств        🟢
1–3                                 🟡
4+                                  🔴
```

Это только первоначальная визуализация.

Пороговые значения вынести отдельно, чтобы их можно было изменить.

## 13. Рейтинг риска

Подготовить систему для внутреннего скоринга контрагента.

Не смешивать рейтинг с исходными данными.

Исходные данные должны храниться отдельно.

Например:

```text
risk_score = 0..100
```

и:

```text
LOW
MEDIUM
HIGH
CRITICAL
```

В интерфейсе:

```text
Риск контрагента

СРЕДНИЙ

58 / 100
```

Первоначальную формулу можно сделать простой.

Например:

```text
падение выручки > 30%             +20 риска
убыток                             +20
активные исполнительные > 3       +20
арбитражных дел > 5               +20
крупная сумма требований           +20
```

Но архитектурно формулу необходимо вынести в отдельный сервис:

```text
CompanyRiskService
```

Например:

```python
CompanyRiskService.calculate(check_data)
```

## 14. Важное требование по UI

Все данные этого блока являются:

```text
SYSTEM / READ ONLY
```

Обычный пользователь не должен видеть поля ввода.

То есть нельзя делать:

```text
Выручка: [___________]
```

Нужно отображать:

```text
Выручка: 151 700 000 ₽
```

Дополнительно показать подпись:

```text
Данные получены автоматически из внешнего источника
```

и:

```text
Последняя проверка: 24.08.2026 12:40
```

## 15. Ошибки внешнего API

Ошибки внешнего сервиса не должны ломать карточку компании.

Если сервис недоступен:

```text
Не удалось обновить данные.

Показаны данные последней успешной проверки от
23.08.2026 14:20.
```

Если компания не найдена:

```text
По указанному ИНН данные не найдены.
```

Если ИНН отсутствует:

```text
Для автоматической проверки необходимо указать ИНН компании.
```
